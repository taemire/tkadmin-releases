31. Bearer 토큰 관리 운영자 매뉴얼

tkadmin v0.8.0 (BL-035) 부터 Bearer 토큰 발급/회수/회전을 웹 UI에서 직접 수행할 수 있습니다. 본 문서는 관리자가 service-account 자동화용 Bearer 토큰을 안전하게 운영하는 방법을 안내합니다.

31.1. 페이지 접근​

  • 메뉴 위치: 사이드바 → 설정 (settings) → Bearer 토큰
  • 직접 URL: /tkadmin/admin/tokens
  • 페이지 노출 권한: view:auth (admin · monitor)
  • 발급/회수/회전 권한: manage:auth (admin)
info

view:auth 권한이 있으면 페이지를 열고 목록·통계를 조회할 수 있지만, 발급/회수/회전 버튼은 manage:auth 권한이 없으면 비활성화됩니다.

31.2. 토큰 발급​

  1. 우측 상단 새 토큰 발급 버튼 클릭
  2. 발급 모달에 다음 항목 입력:
    • Subject: 토큰 사용 주체 식별자 (1~32자, 영문·숫자·_-)
    • Role: admin / monitor / viewer 중 선택 (superadmin 발급은 불가)
    • TTL (sec): 60 ~ 31,536,000 (기본 3,600 — 1시간)
    • Description: 운영 식별용 메모 (선택)
  3. 발급 시 step-up 재인증 모달이 자동으로 뜨면 비밀번호 재입력
  4. 발급 완료 → 평문 토큰이 모달에 1회 노출됨
warning

발급 평문은 1회만 표시됩니다. 모달 닫는 즉시 DOM에서 제거되며, 메모리 캐시도 5분 후 자동 폐기됩니다. 안전한 곳에 즉시 저장하세요.

발급 직후 5분 동안은 페이지 우상단의 노란 배지를 클릭하여 토큰을 한 번 더 확인할 수 있습니다. 5분 경과 후 배지는 자동 제거됩니다.

31.3. 토큰 회수​

  1. 목록에서 회수할 토큰 행의 회수 버튼 클릭
  2. 사유 (optional) 입력 후 확인
  3. step-up 재인증 (활성 상태 유지 시 자동 통과)
  4. 회수 완료 — 해당 토큰을 사용하던 자동화는 즉시 401 응답을 받음
caution

회수는 즉시 반영됩니다. 운영 중인 서비스가 영향을 받을 수 있으므로 회수 전 영향 범위를 확인하세요.

31.4. 키 회전​

서명 마스터 키 (kid) 를 새로 발급하고 기존 키를 retired 상태로 전환합니다. 기존 발급된 토큰은 grace 기간 (90일) 동안 그대로 사용 가능합니다.

  • 사용 시점: 키 노출 의심, 정기 보안 정책 (분기/연간), 테스트 환경 키 분리
  • 권한: manage:auth + step-up
  • Rate limit: 시간당 1회 (전역) — 두 번째 회전 시도는 429 + Retry-After 응답
  • API 직접 호출: POST /api/auth/tokens/rotate-key

키 회전 후 응답에는 new_kid, retired_kid, activated_at 가 포함됩니다.

31.5. 통계 페이지​

상단 탭에서 Stats 선택:

  • Active / Revoked / Expired 카운트 카드
  • Last Used Distribution: 최근 1시간 / 24시간 / 7일 사용 분포
  • By Subject / By Role: 주체·역할별 토큰 수

range 셀렉터로 7d / 30d / all 범위를 변경할 수 있습니다.

31.6. Rate limit (DoS 방어)​

작업제한
발급 (per_subject)분당 10건
발급 (global)분당 100건
회수 (per_subject)분당 20건
키 회전 (global)시간당 1건

제한 초과 시 429 응답 + Retry-After 헤더가 반환되며, UI는 i18n 메시지로 사용자에게 재시도 시각을 안내합니다.

31.7. Encryption-at-rest (DB 보안)​

bearer_signing_keys.secret 컬럼은 AES-256-GCM 으로 암호화되어 DB에 저장됩니다 (BL-035 v0.8.0 부터). 마스터 키는 다음 우선순위로 로드:

  1. 환경변수: TKADMIN_ENCRYPTION_KEY (base64-encoded 32 bytes)
  2. 파일: /usr/local/tkadmin/etc/encryption.key (mode 0600)
  3. systemd Credential: CREDENTIALS_DIRECTORY 동적 조회

여러 source 가 동시에 활성이면 stderr 에 WARN 로그 — 의도된 우선순위인지 운영자가 확인 필요.

마스터 키 회전 (CLI)​

웹 UI 와 별개로, 마스터 키 자체를 회전하는 작업은 CLI 로 수행합니다:

tkadmin secret migrate-status              # 점진 마이그레이션 상태 조회
tkadmin secret migrate-resume              # 실패한 키 재시도 (3회 한도)
tkadmin secret rotate-key --yes            # 마스터 키 회전 — 새 키 stdout 1회 노출 (운영자 수동 keystore 반영)
tkadmin secret rotate-key --yes --update-keystore=file   # BL-036a v0.8.8: file source 자동 갱신 (권장)

rotate-key 는 단일 트랜잭션 내에서 모든 secret_enc 를 새 마스터 키로 재암호화합니다. 새 키는 표준 출력에 1회만 노출됩니다.

BL-036a v0.8.8 — --update-keystore=file (권장)​

옵션흐름운영자 부담사고 위험
--update-keystore=none (default, 기존 v0.8.3 호환)새 키 stdout → 운영자 수동 복사 → file 갱신 → 재시작높음 (수동 4단계)누락 시 복호화 불능
--update-keystore=file (BL-036a 권장)새 키 stdout (백업) + file POSIX atomic rename + 0600 + 재시작 안내낮음 (재시작만)매우 낮음

file 갱신 흐름:

  1. CLI: 기존 키 로드 + 새 32-byte 키 생성
  2. CLI: 단일 트랜잭션으로 모든 secret_enc 재암호화
  3. CLI: os.CreateTemp 동일 dir + write + chmod 0600 + fsync + os.Rename (POSIX atomic)
  4. CLI: stdout 백업 키 1회 출력 (file 갱신 성공 시 폐기 가능)
  5. CLI: audit_logs::keystore_rotation_log 에 keystore_source_updated 이벤트 기록 (file path 만, key bytes 절대 미포함)
  6. 운영자: tkadmin service restart

기본 file 경로: /usr/local/tkadmin/etc/encryption.key. 다른 경로 사용 시 --keystore-path=....

file 갱신 실패 시: stderr 에 명확한 복구 안내 출력 (DB 는 이미 새 키로 재암호화됨 — file 도 반드시 갱신해야 재시작 후 복호화 가능):

1. 위 stdout 의 새 마스터 키 (base64) 를 복사
2. echo '<base64 키>' | sudo tee /usr/local/tkadmin/etc/encryption.key && sudo chmod 0600 ...
3. tkadmin service restart

비표적 (별 BL):

  • env source 자동 갱신 — OS/외부 시스템 책임 (운영자 수동)
  • systemd Credential 갱신 — 외부 시스템 (/run/credentials/<svc>/encryption.key)
  • in-process hot-swap — admin endpoint 신설 필요 (BL-036b 또는 후속 cycle)
  • 자동 재암호화 (90일 경과 시 자동) — BL-036b

HA / multi-instance lock 정책 (v0.8.13 — BL-046)​

tkadmin multi-instance HA 운영 시 cross-instance race 차단할 수 있는 advisory lock 인프라.

Opt-in 활성화​

ha:
  enabled: false            # default — process-local lease (single-instance)
  instance_id: ""           # default — hostname:pid:start_time 자동
  lease_ttl_seconds: 600    # default — BL-041 240s budget + 마진

default false — 명시적 활성화 필수. single-instance 운영 환경 무중단.

적용 대상​

Lock 이름사용처
tachyon-migrateMigratePolicies / MigratePoliciesStream (BL-041/045)
keystore-auto-rotateKeystoreAgeMonitor 자동 회전 (BL-036b 분할 3단계)

두 구현 (자동 분기)​

  • process-local (ha.enabled=false, default): in-memory sync.Mutex — BL-041 V1 호환
  • SQLite advisory lock (ha.enabled=true): DB 기반 — multi-instance race 자연 차단

흐름​

  1. Acquire(name, holder, ttl) — 점유 시도
  2. ErrLockHeld 시 다른 instance 점유 중 — 호출자 retry / 409 응답
  3. 만료 lease 자동 cleanup (Acquire 시점)
  4. Release(lease) — Lease.ID 검증 후 해제

안전망​

  • 만료 lease 자동 cleanup — 좀비 lease 영구 차단 회피
  • holder ID 평문 secret 미포함 (hostname:pid:start_time)
  • Lease.ID crypto/rand (충돌 ~2^64)
  • TTL 0/음수 거부 (무한 lease 위험 차단)

자동 회전 정책 (v0.8.11 — BL-036b 분할 3단계)​

KeystoreAgeMonitor 가 critical 단계 (default 120일 경과) 도달 시 tkadmin secret rotate-key --update-keystore=file 와 동등한 흐름을 자동 실행합니다.

Opt-in 활성화​

keystore:
  rotation_warn_days: 90        # 기존
  rotation_critical_days: 120   # 기존
  auto_rotation_enabled: true   # ⭐ BL-036b 3단계 default false → true 명시
  auto_rotation_actor: scheduler  # 옵션 (default "scheduler")

default false — 명시적 활성화 필수. 잘못된 환경 (file source 미설정 / 운영 시간) 에서 자동 회전이 service 영향을 주는 사고 방지.

자동 회전 흐름​

  1. 자정 + 24h tick 시점에 CheckOverdue 가 critical 단계 감지
  2. race 가드: 최근 24h 내 manual_rotation_started 이벤트 존재 시 skip (운영자 수동 회전과 race 차단). audit auto_rotation_skipped 기록.
  3. auto_rotation_triggered audit 발화 (actor='scheduler', file_path 기록)
  4. rotator.Service.Rotate 호출 — DB 재암호화 + file source POSIX atomic 갱신
  5. 성공: auto_rotation_succeeded audit + KEYSTORE_AUTO_ROTATION_SUCCEEDED alert
  6. 실패: auto_rotation_failed audit + KEYSTORE_AUTO_ROTATION_FAILED critical alert (운영자 즉시 알림 — file 갱신 실패 시 service 영향)

안전망 (다중 보호)​

보호구현
Opt-in (default off)config keystore.auto_rotation_enabled
race 가드 24hmanual_rotation_started 최근 호출 존재 시 skip
단일 writer 락SQLite BEGIN IMMEDIATE — multi-instance race 차단
UpdateKeystore=file 강제autonomous 흐름이라 운영자 수동 복구 불가능 — file atomic 갱신 필수
실패 시 critical alert운영자 즉시 인지 + keystore_rotation_log 기록
평문 키 audit 미노출Notes 에 file_path / actor / age_days 만 (key bytes 절대 X)

운영자 가이드​

  • 활성화 권장 환경: file source 표준 경로 (/usr/local/tkadmin/etc/encryption.key) 사용 + master key 가 file 만 (env / systemd 미사용)
  • 활성화 비추천 환경: env source / systemd Credential 사용 (자동 file 갱신이 의미 없음 — 운영자 OS 측 갱신 필요)
  • 모니터링: keystore_rotation_log 의 event_type IN ('auto_rotation_*') 추적
  • 수동 비활성: auto_rotation_enabled: false + tkadmin service restart

회전 영향 범위 (v0.8.9 — BL-036c)​

reencryptAllSecrets 가 단일 트랜잭션 내에서 다음을 모두 재암호화합니다:

대상도입 BL처리 조건
bearer_signing_keys.secret_encBL-035 v0.8.0WHERE secret_enc IS NOT NULL
tachyon_credentials.token_encBL-041d v0.8.6auth_mode='bearer' AND len(token_enc)>0 AND alg!='none'
tachyon_credentials.password_encBL-040b v0.8.7auth_mode='jwt' AND len(password_enc)>0 AND alg!='none'

부분 실패 시 rollback — 단일 트랜잭션이라 bearer 처리 후 tachyon 실패 시 bearer 도 자동 rollback. DB 일관성 보장.

빈 BLOB skip — BL-040b 의 INSERT 패턴 (JWT mode 시 token_enc=[]byte{} + alg='none') 회피. Decrypt 호출 안 함.

이전 v0.8.8 의 임시 절차 (운영자가 회전 전 tachyon_credentials 임시 폐기 → 회전 → 재등록) 는 불필요 — 한 번의 tkadmin secret rotate-key --yes --update-keystore=file 로 모든 envelope-encrypted secret 자동 재암호화 + file source atomic 갱신 + 재시작 1회.

31.8. 트러블슈팅​

증상원인조치
발급 버튼이 비활성화manage:auth 권한 부재RBAC 관리에서 사용자 역할에 manage:auth 부여
발급 시 즉시 403 모달step-up 만료비밀번호 재입력 모달에서 재인증
429 + "요청 빈도 초과" toastRate limit 도달표시된 Retry-After 초만큼 대기 후 재시도
회전 시 "concurrent_rotation"다른 운영자가 동시 회전 시도1초 후 재시도 (트랜잭션 충돌 자동 회피)
마이그레이션 permanently_failed3회 실패한 키tkadmin secret migrate-status 로 키 ID 확인 후 운영팀 에스컬레이션

31.9. 보안 정책 캐리오버 (BL-034)​

  • Bearer 자기 토큰 발급 차단: Bearer 인증으로 들어온 요청은 RequireElevation 가 즉시 403 (bearer_no_elevation). 본 페이지의 모든 발급/회수/회전은 cookie 세션으로만 가능.
  • superadmin role 발급 거부: 정책상 superadmin 권한 Bearer 토큰은 발급할 수 없음 (403 + superadmin_rejected).
  • 응답 본문 평문 부재: GET 응답에는 토큰 평문이 포함되지 않으며, fingerprint (SHA-256[:12]) 만 노출.
  • Audit: 모든 발급/회수/회전 이벤트는 audit_logs 테이블에 service='auth' type LIKE 'bearer.%' 로 기록됨.
